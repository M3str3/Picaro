# Plan — flat runtime steps (schema 6)

**Status: landed (2026-09-28).** The loader is one ordered `runtime:` list of
technique steps. There are no stages, no nested pipelines and no single
`build.payload`. Reference: `docs/multistage.md`. Rolling state: `.memory.md`.

The superseded schema-5 design (`stages:` with `technique`/`exec`/`sleep`
actions, `build.payload` normalization) is gone: every schema-5 document is
rejected at parse time with one migration hint (`RETIRED_SCHEMA_MIGRATION` in
`src/plan/schema.rs`). The x86 plan is preserved as `.plan.x86.md`.

---

## 0. The hard constraint (still the shaping rule): which steps return control

A chain only continues if the loader gets control back after a step. This is a
property of the technique and the payload, not a flag:

| Step | Returns control? | Why |
| --- | --- | --- |
| `living_off_the_land` | **Always** | The loader spawns a child and keeps running. |
| `process_hollowing` | **Always** | A separate process; the loader waits and reads its exit status. |
| `reflective_loading` + `dll` | **Always** | A mapped DLL's entry point is `DllMain`, which returns. |
| `reflective_loading` + `shellcode` | **If the shellcode returns** | It runs on its own thread; a beacon that never returns blocks the chain. |
| `reflective_loading` + `pe` (an EXE) | **No** | The entry point runs on the stub's thread and a normal `mainCRTStartup` calls `ExitProcess`. |
| `dotnet_hosting` | **No** | The CLR is hosted in the stub's process; a managed `Main` that exits ends it. |

A **terminal** step (`reflective_loading` of a PE executable, or
`dotnet_hosting`) can only be the **last** one; `plan::validate` rejects it
otherwise.

## 1. A step is the lego

```yaml
runtime:
  - technique: <name>
    params: { ... }          # the technique's own arguments
    on_success: continue     # loader orchestration (StepControl)
    on_fail: stop
    delay_ms: 0
```

- `params` is what the technique interprets; the control fields are the loader's
  policy and are deliberately kept out of `params`.
- `TechniqueKind` (the internally-tagged enum) holds the per-technique `params`;
  `RuntimeStep { technique, control }` pairs it with `StepControl`
  (`src/techniques/mod.rs`).
- `exec` is the technique `living_off_the_land` (`binary`/`args`/`window`/
  `wait`/`timeout_s`); `sleep` is the technique `sleep` (`ms`). Both are
  `Category::Control`.

## 2. Payloads: a named map with inherited crypto

- `build.payloads` is a `BTreeMap<name, PayloadPlan>`; `build.crypto` is the
  default a payload inherits when it omits its own `crypto`.
- An Execution step selects its payload with `params.payload`. With exactly one
  payload the name is optional; with two or more it is required and checked.
  `src/plan/steps.rs::resolve` pins each Execution step to a

`ResolvedPayload { name, plan, crypto }`.

## 3. Where it lives

- Resolution: `src/plan/steps.rs` (`resolve` → `Vec<ResolvedStep>`).
- Validation: `src/plan/validate.rs` (step-based; terminal rule over the list;
  proxy `api_resolution` requires exactly one Execution step).
- Rendering: `src/engine/steps.rs` over the single
  `templates/stub/main.rs.tpl` (per-step `mod step_<i>`, a generated runner, the
  shared `$SYSCALLS_BLOCK$`/`$ARGS_BLOCK$`/`$IMPORTS_BLOCK$`/`$API_RESOLUTION_BLOCK$`).
- Build: one path in `src/main.rs`; per-step manifest (`StepRecord`).
- Custom stubs (`build.stub.path`) render through the same engine with
  `$STUB_HELPERS$`/`$STEP_MODULES$`/`$STEP_RUNNER_BODY$` (`docs/custom-stubs.md`).

## 4. Follow-ups

- A run-time network stager, an `ExitProcess` interceptor so two EXEs can chain
  in-process, and a wizard flow for multi-step runtimes (the wizard still writes
  a single-payload plan).
- In-process chaining leaves the process dirty (an unfreed mapped image, a leaked
  `TlsAlloc` index, a repatched PEB command line). Prefer process-based steps
  (`living_off_the_land`, `process_hollowing`) when chaining more than one
  Execution step.
- A shellcode step only chains if the shellcode returns.
