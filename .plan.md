# Plan — multi-payload stages (schema 5)

**Status: M0–M2 landed on branch `experimental-multi-stage` (2026-09-28).**
Landed: schema 5 with `stages:` (`technique`/`exec`/`sleep`), `build.payload`
optional + normalization (`src/plan/stages.rs`), per-stage validation (terminal-
stage rule, proxy rejection, exec checks), the multi-stage renderer
(`src/engine/stages.rs` + `templates/stub/main_stages.rs.tpl`), `build_multistage`
in `src/main.rs`, and the `exec`/living-off-the-land action. Verified by a real
compile test and an end-to-end build (`examples/plans/multistage.yaml`). Not yet:
the run-time network stager, an `ExitProcess` interceptor, and the wizard flow.
Landed after the first pass: per-stage payload args (a thread-local stage
context), the LOLBin catalogue + advisory, and a stages-aware manifest.

Derived from a code audit of picaro
(2026-09-28): `PayloadPlan`/`BuildPlan { payload, stub, output }`
(`src/plan/schema.rs`), the single-payload stub
(`templates/stub/main.rs.tpl`: `NONCE_HEX`/`KEY_HEX`/`PLAINTEXT_LEN`/`PAYLOAD_ENC`
and one `execute_payload`) and `StubParams` (`src/engine/stub.rs`). The x86 plan
that preceded this file is preserved as `.plan.x86.md`.

Goal: one plan delivers **several payloads** through an ordered chain of
**stages**, where each stage is an action — run an embedded payload with a
technique pipeline (today's model), launch a command / living-off-the-land (LOL)
binary (new), or wait — orchestrated with per-stage gating on exit codes,
delays and failure policy.

The canonical deliverables are the schema (a document, so a migration is doc
only for most plans), the generated stub's stage runner, and the `exec` action.

---

## 0. The hard constraint (read first): which stages return control

A chain only works if the loader gets control back after a stage. This is not a
property of the packer; it is a property of the action and the payload, and the
audit settled it precisely:

| Stage action | Returns control? | Why |
| --- | --- | --- |
| `exec` (process spawn) | **Always** | The loader spawns a child and keeps running. |
| `process_hollowing` | **Always** | It is a separate process; the loader waits and reads its exit status. |
| `reflective_loading` + `format: dll` | **Always** | `execute_entrypoint` only runs `DllMain(DLL_PROCESS_ATTACH)`, or calls a named export, and returns. |
| `reflective_loading` + `format: shellcode` | **If the shellcode returns** | `run_shellcode` runs it on its own thread and `WaitForSingleObject`s. A shellcode that calls `ExitProcess` or beacons forever does not return. |
| `reflective_loading` + `format: pe` (an EXE) | **No, in practice** | The entry point is called on the stub's own thread (`stub_fragment.rs::execute_entrypoint`, L685-707) and a normal `mainCRTStartup` calls `ExitProcess`, killing the whole process. The fragment says so: *a payload that calls `ExitProcess` ends the process*. |
| `dotnet_hosting` | **No, in practice** | The CLR is hosted in the stub's process; a managed `Main` that exits terminates the process. |

Consequences, and the reason the schema has a "terminal stage" rule:

- A chain is reliable when every **non-terminal** stage is `exec`,
  `process_hollowing`, or a returning `reflective_loading` (`dll`, cooperative
  `shellcode`).
- A `reflective_loading` **PE/EXE** stage or a `dotnet_hosting` stage can only be
  the **last** stage: it hands the process over and the loader never returns.
- Even a returning in-process stage leaves the process dirty (a mapped image that
  is never freed, a leaked `TlsAlloc` index, a permanently repatched PEB command
  line via `patch_command_line`). Multi-stage **in-process** chaining needs
  per-stage cleanup; multi-stage **by processes** (`exec`, hollowing) does not.

This shapes everything below: `exec` and process-based techniques are the
chainable primitives; `reflective_loading` PE is a terminal stage.

## 1. Decision: a stage is an action

Today `runtime` is `0..N` Preparation plus **exactly one** Execution that
consumes the decrypted payload. A LOL command ("spawn a signed binary with these
arguments") **does not fit as an Execution**: it consumes no payload, and a plan
may have no payload at all. Forcing it would break the `1 Execution` invariant
and the `execute_payload` contract.

So a **stage** is a tagged *action*:

- `action: technique` — the current pipeline (0..N Preparation + 1 Execution).
- `action: exec` — spawn a process (T1218 proxy execution / T1059 command).
- `action: sleep` — wait (reuses the `sleep_obfuscation` machinery).

Validation rule: **every `technique` stage has exactly one Execution; `exec`
and `sleep` stages have none.**

Rejected alternative (recorded in §11): `technique: lolbin_exec` as a registry
technique inside `runtime`. It is more uniform with the registry but breaks the
`1 Execution` invariant and cannot express a payload-less plan.

## 2. Schema (schema 5)

The payload catalogue is separated from the orchestration, and **the point is
to pack several payloads into one artifact**: two shellcodes, two EXEs, or a
mix. Each stage names one payload `id` and the execution technique that runs it.

Canonical example — **two shellcodes in one stub**:

```yaml
schema: 5
name: two-shellcode

build:
  payloads:
    - id: dropper
      source: ./stage1.bin
      format: shellcode
      crypto: { algo: xchacha20poly1305, key: random }
    - id: implant
      source: ./stage2.bin
      format: shellcode
      crypto: { algo: xchacha20poly1305, key: random }
  output:
    path: ./dist/two_shellcode.exe
    arch: x64
    strip: true
  stub:
    strings: { strategy: xor, key: random }

stages:
  - name: dropper
    action: technique
    payload: dropper
    runtime: [{ technique: reflective_loading }]
    on_success: continue

  - name: implant
    action: technique
    payload: implant
    runtime: [{ technique: reflective_loading }]
```

**Two EXEs in one stub** — both run in their own process, because a reflectively
loaded EXE calls `ExitProcess` (§0):

```yaml
build:
  payloads:
    - { id: a, source: ./a.exe, format: pe, crypto: { algo: xchacha20poly1305, key: random } }
    - { id: b, source: ./b.exe, format: pe, crypto: { algo: xchacha20poly1305, key: random } }
  output: { path: ./dist/two_exe.exe, arch: x64, strip: true }

stages:
  - name: a
    action: technique
    payload: a
    runtime:
      - technique: process_hollowing
        params: { target: "C:\\Windows\\System32\\svchost.exe" }
    on_success: continue

  - name: b
    action: technique
    payload: b
    runtime:
      - technique: process_hollowing
        params: { target: "C:\\Windows\\System32\\dllhost.exe" }
```

**Mixed** — a returning in-process stage followed by a process-based one:

```yaml
stages:
  - { name: shellcode, action: technique, payload: dropper, runtime: [{ technique: reflective_loading }] }
  - { name: exe, action: technique, payload: b, runtime: [{ technique: process_hollowing, params: { target: "C:\\Windows\\System32\\dllhost.exe" } }] }
```

### What can actually be chained (ties §0 to the schema)

| Combination | Chainable? | How |
| --- | --- | --- |
| 2 shellcodes | Yes **if both return** | `reflective_loading` runs each on its own thread; a beacon/`ExitProcess` shellcode does not return. |
| 2 EXEs | Yes — each in its own process | `process_hollowing` per stage. Reflective-loading both is **not** possible (the first EXE's `ExitProcess` kills the stub). |
| shellcode + EXE | Yes if the shellcode returns | Shellcode `reflective_loading` first, EXE hollowed second. The reverse makes the EXE terminal. |
| EXE reflectively + anything | **No** | The EXE stage is terminal (hard validation error). |
| drop + `exec` | Yes | A stage writes/embeds a payload and an `exec` stage launches it as a child process. |

Chaining two *reflectively loaded EXEs* in one process needs an
`ExitProcess`/`TerminateProcess` interception so a stage's exit returns to the
loader instead of killing it. That is a separate workstream (M6, §9), not
covered by the stage runner.

### Back-compatibility (normalization)

A schema-4 single-payload document is accepted verbatim in schema 5 and
normalized internally to one payload and one stage:

```yaml
schema: 5
build:
  payload: { source: ./p.exe, crypto: { algo: xchacha20poly1305, key: random } }
  output: { path: ./dist/o.exe, arch: x64, strip: true }
runtime:
  - technique: patch_amsi
  - technique: reflective_loading
```

normalizes to `payloads: [ { id: "default", ...payload } ]` and
`stages: [ { name: "default", action: technique, payload: "default",
runtime: [...] } ]`. A schema-4 document is rejected at parse time with a
migration hint (`docs/migration-v4-v5.md`), and the hint's message is "add
`schema: 5`; a single-payload plan needs no other change". The rest of
`build.stub`/`build.output` is unchanged; `build.stub.syscalls` becomes the
**union** of every stage's `TechniqueDef::syscalls`.

Why bump to 5 and reject 4: it matches the repo's convention (each schema bump
rejects the previous one with a hint) and keeps one canonical shape. The cost is
a doc-only edit for the overwhelming majority of plans.

## 3. The `exec` action (living off the land)

| Field | Default | Meaning |
| --- | --- | --- |
| `binary` | — | A bare name (`certutil.exe`, resolved at run time against `System32`/`SysWOW64`/`PATH`) or an absolute path. |
| `args` | `[]` | Arguments; rebuilt at run time through `StringsConfig` (same treatment as `build.payload.args`). |
| `wait` | `true` | `true`: wait and capture the exit code (enables gating). `false`: detach (the loader keeps control at once). |
| `window` | `hidden` | `hidden` → `STARTUPINFOA` with `STARTF_USESHOWWINDOW`/`SW_HIDE` plus `CREATE_NO_WINDOW`; `normal` → inherit the console. |
| `timeout_s` | `0` | `0` = no limit; on expiry the child is terminated. |
| `on_success` / `on_fail` | `continue` | `continue` \| `stop` \| `exit` \| `retry(N)` (with `delay_ms` between attempts). |
| `delay_ms` | `0` | Wait before launching. |

Properties:

- **Mechanism.** `CreateProcessA` (already used by hollowing and kept Win32 —
  a loader entry point, not a kernel call the stub issues; AGENTS.md). No PEB
  command-line patch is involved: the child has its own command line.
- **Resolution.** A bare `binary` is resolved explicitly against
  `GetSystemDirectoryW`/`GetSystemWow64DirectoryW` first (then `PATH`), so the
  known-system-binary path is chosen and cwd/hijack resolution by
  `CreateProcessA` does not win.
- **Strings.** The binary name, every argument and the assembled command line go
  through `StringsConfig`; the `no_sensitive_literals_in_generated_stubs` guard
  covers them. The fragments ship no cleartext literal.
- **OPSEC (documented, not hidden).** The child's command line is visible to a
  process-level observer, and the child's parent is the stub (`ppid_spoofing` is
  the follow-up, README roadmap). `window: hidden` only removes the window, not
  the process.

A LOLBin catalogue (a curated list: `certutil`, `bitsadmin`, `curl`, `rundll32`,
`regsvr32`, `mshta`, `wmic`, `msbuild`, `msiexec`, `schtasks`, `forfiles`,
`pcalua`, `xwizard`, …) produces **advisories**, never a hard error: a `binary`
outside the list draws a warning at build time and shows in `--dry-run`.

## 4. Validation (`src/plan/validate.rs`)

Per stage (reusing `validate_runtime` for `technique` stages):

- exactly one Execution in a `technique` stage; `exec`/`sleep` declare no
  `runtime`;
- `payload` resolves to a catalogue `id` (or the single entry when omitted);
- format/technique coupling per stage (`process_hollowing` is `pe`-only,
  `dotnet_hosting` ⇔ `format: dotnet`, `export` needs `format: dll`, …);
- capability and arch checks per stage against the shared `build.output.arch`;
- each `format: pe`/`dll`/`dotnet` payload's arch must match `output.arch`.

Chain-level:

- **Terminal-stage rule (hard error):** a `reflective_loading` stage with
  `format: pe`, or a `dotnet_hosting` stage, must be the **last** stage. Message
  states the technique does not return control and points at `process_hollowing`
  or `exec`.
- **Advisory:** a `reflective_loading` `format: shellcode` stage that is not last
  (it may not return).
- **`api_resolution.mode: proxy` is loader-wide** (the proxies live in the loader
  and rewrite the process's own IAT), so it is rejected on a multi-stage plan in
  v1 — it is meaningful for at most one stage.
- `run_if`/`on_*` references resolve to a known stage; `retry(N)` has `N >= 1`;
  no stage references a later stage (no forward dependencies).

## 5. Stub rendering (`src/engine/stub.rs`, `templates/stub/main.rs.tpl`)

- `$PAYLOAD_BYTES$` → **`$PAYLOADS_BLOCK$`**: one `include_bytes!` per stage plus
  a `const STAGES: &[StageInit]` table (nonce, key, ciphertext, plaintext length,
  format, export). Each payload keeps its own key/nonce.
- **Execution fragments are namespaced.** Today `$EXECUTION_BLOCK$` is injected at
  the top level and the template calls `execute_payload` unqualified. Each
  `technique` stage's fragment is wrapped in `mod stage_<id> { ... pub fn
  execute_payload(&mut [u8]) -> Result<i32, String> }` (the same trick already used
  for Preparation blocks) and the generated runner calls
  `stage_<id>::execute_payload`. Without this, two execution fragments collide on
  their top-level names.
- `$ARGS_BLOCK$` / `$IMPORTS_BLOCK$` become **per stage** (each stage has its own
  payload args), or are parameterized (`patch_command_line(args)`). `$SYSCALLS_BLOCK$`
  stays single (`init_syscalls` runs once over the union).
- **`$EXEC_BLOCK$` (new)** renders the `exec` launcher (process spawn, window
  hiding, wait/timeout, exit-code read).
- **`$STAGE_RUNNER$` (new)** replaces the tail of `run()`: iterate `STAGES`, run
  the stage action, apply `on_success`/`on_fail`/`delay_ms`, capture the exit
  code, and exit with the last stage's code.
- **Per-stage marker.** `$STUB_MARKER_DEF$` becomes one marker per stage (kept
  for verification: each stage prints its own identity on stderr after decrypting).

Format-specific choice inside a stage follows the existing
`RuntimeStep::render_fragment_for(strings, format, export)`.

## 6. Build flow (`src/main.rs::build`, `src/engine/manifest.rs`)

`build` is already ~420 lines (L334-758). Multi-stage turns its body into a loop,
so **extract sub-steps first** (§7 workstream F) rather than growing it:

1. read + validate + (optional `sha256` pin) every payload;
2. encrypt every payload (independent key/nonce);
3. render the stub (payload table, stage modules, exec block, runner);
4. compile once (single `rustc` invocation), embed resources, sign;
5. write the manifest with a **per-stage** record: `id`, `format`, `sha256`,
   `techniques`, `action`.

`--dry-run` prints the resolved chain (stage order, action, technique, payload,
gating) without encrypting, compiling or writing.

## 8. Limitations to document (explicitly)

1. **A non-returning stage must be last.** `reflective_loading` PE/EXE and
   `dotnet_hosting` hand the process over; a following stage never runs (a hard
   validation error, not a silent no-op).
2. **In-process chaining leaves the process dirty** (unfreed mapped image, a
   leaked TLS index, a repatched PEB command line). Prefer process-based stages
   when chaining more than one technique stage.
3. **`exec` spawns a visible child** process (PPID = the stub, command line
   observable); `window: hidden` hides the window only. `ppid_spoofing` is the
   follow-up.
4. **`api_resolution.mode: proxy` is single-stage** (loader-wide IAT rewrite).
5. **Payloads are embedded by default**, so the artifact grows with every stage;
   a run-time network stager (fetch the next stage in the stub) is Phase M5.
6. `build.output.arch` is shared; a `shellcode` stage still follows it (no arch in
   the bytes).
7. **Two reflectively loaded EXEs cannot be chained** in one process without
   intercepting `ExitProcess`/`TerminateProcess` (M6); use `process_hollowing`
   per stage instead.
8. **A shellcode stage only chains if the shellcode returns.** A beaconing or
   `ExitProcess`-calling shellcode does not, and validation can only advise.
   Running two *non-returning* shellcodes needs a process-per-stage injection
   technique (each shellcode in its own spawned process) — `early_bird`/
   shellcode-injection territory, not implemented today.

- **M0 — schema + normalization + validation + `--dry-run`.** DONE. `schema: 5`
  and the legacy `schema: 4` are both accepted; a schema-4 document normalizes to

## 11. Open questions (recommendations)

- **Schema:** bump to 5 and reject 4 with a helper hint (**recommended**), vs.
  staying additive in 4. Recommendation: 5.
- **Form:** `action: technique|exec|sleep` with `stages:` (**recommended**), vs.
  `technique: lolbin_exec` inside `runtime`. Recommendation: the action model — it
  keeps the `1 Execution` invariant and allows payload-less stages.
- **`exec` default `wait`:** `true` (**recommended**, gating-first), vs. `false`.
- **`payloads:` + `stages:`** vs. payload inline per stage. Recommendation: the
  catalogue — it deduplicates and lets the order change without rewriting blocks.
- **LOLBin list:** advisory (**recommended**), not a hard allow-list.
- **`exec` mechanism:** `CreateProcessA` (**recommended**, consistent with
  hollowing), vs. `ShellExecuteExW` (shell semantics, worse OPSEC).
