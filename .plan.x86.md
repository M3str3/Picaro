# Plan — x86 (32-bit) support

**M0–M5 are done — 2026-09-27. M4 (x86 indirect syscalls and `sleep_obfuscation`)
stays parked, with the reasons in §4.**
§2.F (the technique fragments), §2.G (API resolution), §2.H (.NET) and §2.I
(tooling) are the workstreams that changed; the rest of the plan is history and
stays as written.

What landed, verified end to end on Windows (see `docs/x86.md` and
`docs/measurements.md`):

- **M1** — `reflective_loading` maps and runs a PE32 payload in the 32-bit stub.
- **M2** — `process_hollowing` hollows a 32-bit target (the WOW64
  `svchost.exe`): the payload writes its marker, reads `tls=42` and its exit
  code comes back through the stub.
- **M3** — `anti_debug` (x86 debug registers), `patch_amsi`, `patch_etw` and
  `bouncer` run in a 32-bit stub before the payload.
- **M5** — `dotnet_hosting` hosts the CLR in the stub and runs a managed payload
  from memory (`format: dotnet`); the x86 and x64 paths are covered, and
  `SharpHound.exe` (x86 .NET) is an acceptance test.

Two findings that were not in the plan and that shaped the port:

1. **TLS provisioning was broken on both architectures.** picaro gave a mapped
   image a `TlsAlloc` index and set the block with `TlsSetValue`, which writes a
   *different* array than the one a CRT reads (`gs:[0x1480]` / `fs:[0xE10]` vs
   `gs:[0x58]` / `fs:[0x2C]`), so a payload's `thread_local` reads returned
   another module's data. The block now goes into the loader's array, and the
   index is reserved through `TlsAlloc` because ntdll's thread teardown faults
   on an unreserved entry. Measurements: `docs/measurements.md`.
2. **The plan's premise about x86 TLS was wrong** (§2.F said the 32-bit slots are
   inline in the TEB at `fs:[0xE10]`): that array belongs to
   `TlsAlloc`/`TlsSetValue`; the array `_tls_index` addresses is `fs:[0x2C]` on
   x86 and `gs:[0x58]` on x64, with pointer-sized entries.

M0 acceptance, both verified:

- picaro compiles a valid i686 stub: ignored tests `compiles_an_i686_stub` and
  `compiles_the_shared_blocks_for_i686` (the latter compiles the x86 branches of
  `$ARGS_BLOCK$`/`$IMPORTS_BLOCK$`/`$SYSCALLS_BLOCK$` for i686);
- an x86 plan with an x64-only technique fails validation with a clear message
  (`technique 'reflective_loading' does not support build.output.arch 'x86' yet:
  … this technique has no x86 fragment`), and an arch mismatch between the stub
  and the payload fails in `inspect_payload`.

Next: **M1 — `reflective_loading` x86** (the first technique fragment).

Status of the rest: **plan only.** Derived from a code audit of picaro
and from the working reference implementation in `void-loader`
(`code_examples/void-loader`, branch `origin/experimental`,
`crates/mounterlib/src/execution/{local_pe.rs,process_hollowing.rs}`).

Review notes (2026-09-27) applied: the x86 entry hand-off is **`Eip`**, not
`Eax` (verified against the reference — see §F); x86 SEH, the stub template and
WOW64 filesystem redirection are now explicit workstream items (§D, §F, §3).

Goal: `build.output.arch: x86` produces a real 32-bit packed PE that runs a
32-bit payload, with the same technique set the x64 path already has (minus the
parts that are genuinely x64-only, which are listed as limitations).

## 0. The hard constraint (read first)

**Reflective loading cannot cross architectures.** 32-bit code cannot run in a
64-bit process and vice versa. `void-loader` makes this explicit: its dispatcher
is a compile-time `#[cfg(target_arch = "x86")]` split and it bails with
*"32-bit PE requires a 32-bit mounter"* (`local_pe.rs::inject_and_execute`).

Consequences for picaro:

- `arch` is the **stub** architecture (and therefore the output artifact's).
  The payload must match it. `arch: x86` ⇒ 32-bit stub ⇒ 32-bit payload.
- A 32-bit stub runs on 64-bit Windows under **WOW64**; a 64-bit stub cannot run
  on 32-bit-only Windows.
- Process hollowing is the exception that *can* cross: a 64-bit stub can drive a
  32-bit (WOW64) target. See §1.

Everything below assumes "matching arch" (strategy A) unless stated otherwise.

---

## 1. Decision: how `process_hollowing` gets x86

Two viable designs; pick one before touching the fragment.

- **A — matching arch (recommended).** `arch: x86` ⇒ 32-bit stub, hollowing a
  32-bit target (`hollow_process32` in the reference). Native CONTEXT32, no
  WOW64 layer. Consistent with the `arch` field and with `reflective_loading`.
- **B — x64 stub, WOW64 target.** Keep the stub 64-bit and hollow a 32-bit
  target with `Wow64Get/SetThreadContext`, PEB32 offsets and 32-bit IAT/reloc
  walks (`hollow_process32_from_64` in the reference). Decouples stub arch from
  payload arch, but makes `arch` ambiguous and adds a second hollowing code path.

Recommendation: **A**, and document B as the escape hatch if a 64-bit stub must
deliver an x86 payload.

- [x] Record the decision (A or B) here and in `AGENTS.md`: **A** (matching
      arch). `arch` remains the stub's (and artifact's) architecture and the
      payload must match it; strategy B stays documented as the escape hatch, not
      implemented, so no `build.payloads.<name>.arch` field was added.

### E. Syscall layer (`build.stub.syscalls`)

- [x] **x86 indirect is a separate implementation, not a flag.** The x64 path
      relies on a `syscall; ret` gadget and a `global_asm!` trampoline with the
      x64 ABI; on x86 there is no `syscall` instruction in that form, and the
      SSNs come from the **32-bit** ntdll (WOW64). A Hell's Gate/Tartarus/API-hash
      variant for x86 needs its own resolver and call mechanism (e.g. the 32-bit
      ntdll stub's `mov eax, ssn; call edx` gadget).
- [x] Until then: reject `syscalls.mode: indirect` with `arch: x86` (validation
      error, not a silent downgrade) and document it.
- [x] `api_resolution.mode: proxy` requires indirect ⇒ also x64-only for now;
      gate the same way.

### F-bis. Cross-cutting: x86 SEH and the exception directory

x86 uses **stack-based SEH** (`fs:[0]` → `EXCEPTION_REGISTRATION_RECORD` chain);
x64 uses **table-based SEH** (`.pdata`/`.xdata` + `RtlAddFunctionTable`). Facts
that matter here:

- picaro does **not** register function tables for a mapped image even on x64,
  so payload exception unwinding inside a reflectively loaded image is already
  unsupported there (the reference does register them, x64 only:
  `register_function_table64`).
- On x86 no registration is needed: the payload sets up its own `fs:[0]` chain
  once it runs. Conversely, nothing in the stub should manipulate `fs:[0]`.
- `IMAGE_DIRECTORY_ENTRY_EXCEPTION` is not a meaningful directory in PE32 — do
  not use it to drive x86 logic.
- The stub is compiled with `-C panic=abort`, so it emits no unwinding tables of
  its own; a fragment must not rely on `catch_unwind` (none does today).
- No fragment catches exceptions today (`anti_debug` included), so this is a
  constraint to preserve, not a migration.

- [x] Document the x64/x86 SEH difference in the x86 docs page and in the
      `reflective_loading`/`process_hollowing` READMEs.
- [x] Not attempted (nothing changed here): if payload unwinding is ever wanted,
      the x64 side needs
      `RtlAddFunctionTable` first; x86 does not.

## 3. Limitations to document (explicitly)

1. **Arch must match.** Reflective loading of a 32-bit payload needs a 32-bit
   stub; a 32-bit payload cannot run in a 64-bit process. `arch: x86` ⇒ 32-bit
   stub ⇒ 32-bit payload.
2. **`arch: x86` is a 32-bit artifact.** On 64-bit Windows it runs under WOW64;
   a 64-bit stub cannot run on 32-bit-only Windows.
3. **`syscalls.mode: indirect` is x64-only** until a 32-bit syscall path exists
   (no `syscall; ret` gadget on x86; WOW64 SSNs differ). Consequently
   **`api_resolution.mode: proxy` is also x64-only** for now.
4. **`process_hollowing` needs an arch-matching target.** The target image must
   be 32-bit for an x86 payload. Under WOW64 the `System32\svchost.exe` literal
   is redirected to `SysWOW64\svchost.exe`, so the default happens to work — but
   it is implicit, and a target given as `$arg.N$` cannot be checked at build
   time.
5. **`sleep_obfuscation` (ekko) is x64-only** until ported (x64 ABI + ROP chain).
6. **TLS callbacks under hollowing are still not run** (pre-existing; a
   never-started thread has no TLS array).
7. **.NET assemblies are not native PE execution** — they need CLR hosting.
   SharpHound (x86 .NET) needs both x86 *and* .NET support.
8. **`shellcode` has no arch in its bytes**, so its arch must be declared or
   assumed from `output.arch`.
9. Resources, signing, hashing and `audit` are arch-neutral (no limitation;
   `audit` was fixed to read PE32 this session).
10. **WOW64 filesystem redirection.** An x86 stub sees `System32` as
    `SysWOW64`; this is usually what you want (32-bit ntdll, 32-bit svchost) but
    it is implicit, and a 64-bit packer reading the same path on disk sees the
    64-bit file — so any build-time target/arch check must account for it.
11. **x86 SEH is stack-based.** No `.pdata` registration is needed on x86 (and
    `IMAGE_DIRECTORY_ENTRY_EXCEPTION` is not meaningful in PE32), but payload
    exception unwinding in a mapped image is unsupported on x64 today (no
    `RtlAddFunctionTable`) and is a separate feature.

## 4. Milestones (minimal viable path first)

- **M0 — foundations. DONE.** PE32 parsing, schema/validation coupling,
  capability gating, i686 compiler support, PE32 imports, x86 args, fixtures.
- **M1 — `reflective_loading` x86. DONE.** 32-bit mapper + x86 TLS; a 32-bit
  payload runs and reads its own `thread_local`
  (`packs_and_runs_an_x86_reflective_payload`).
- **M2 — `process_hollowing` x86. DONE.** CONTEXT32 + 32-bit target (strategy A);
  a 32-bit payload hollowed into the WOW64 `svchost.exe` writes its marker, reads
  `tls=42` and its exit code comes back through the stub
  (`packs_and_runs_an_x86_hollowed_payload`). The x64 hollowing path gained the
  same end-to-end test (`packs_and_runs_a_hollowed_payload`).
- **M3 — preparation techniques x86. DONE.** `anti_debug`, `bouncer`,
  `patch_amsi`/`patch_etw` marked and tested
  (`x86_preparations_run_before_the_payload`); `sleep_obfuscation` stays
  x64-only, as planned.
- **M4 — the hard x64-only bits. PARKED, deliberately.**
  - *x86 indirect syscalls:* a 32-bit process cannot execute `syscall` (it runs
    in compatibility mode, where the instruction is invalid), so the only way in
    is Heaven's Gate — a far transfer to the 64-bit code segment around a
    hand-written 64-bit thunk. On top of that, the SSNs readable from the live
    32-bit `ntdll` stubs are the **WOW64** service numbers, which the kernel maps
    through its own table and which are *not* what the 64-bit `syscall` path
    expects; resolving the real ones means reading the 64-bit `ntdll`, which is
    mapped above 4 GB and unreachable from 32-bit pointers. That is a redesign of
    the syscall layer (gate thunk + 64-bit SSN resolution), not a flag.
    `syscalls.mode: indirect` is rejected on x86 (M0) and `api_resolution`
    (which requires indirect) stays x64-only.
  - *`sleep_obfuscation` x86:* unchanged, x64-only by declaration.
- **M5 — .NET hosting. DONE.** `SharpHound.exe` (the assembly in the repo root)
  is a **32-bit .NET assembly** (machine `0x014c`, PE32, COM descriptor present).
  A managed assembly is not native PE execution: its entry point calls
  `mscoree.dll!_CorExeMain`, which starts the CLR for the *process's main module*
  — the stub, not the mapped payload — so reflective loading maps it and then
  fails inside the CLR. picaro now hosts the CLR in the stub
  (`CLRCreateInstance` → `ICorRuntimeHost` → `_AppDomain.Load_3(byte[])` →
  `GetEntryPoint` → `Invoke_3`) and runs the assembly from memory. A managed
  payload declares `build.payloads.<name>.format: dotnet` and the `dotnet_hosting`
  execution technique (both are required; each is a build-time error without the
  other), and the bitness is checked against `output.arch`. Verified:
  `packs_and_runs_a_managed_payload` (x86, args, `x64=False`, exit 42),
  `packs_and_runs_a_managed_payload_on_x64` (AnyCPU on the 64-bit CLR) and
  `packs_and_runs_sharphound` (the packed assembly behaves like the unpacked
  one).

## 6. Open questions — closed

- Strategy A vs B for hollowing (§1): **A** (matching arch). `arch` stays the
  stub's architecture; B is documented as the escape hatch, not implemented.
- Payload arch for `shellcode`: implied by `output.arch` (the field was not
  added). **Open risk, by decision:** a shellcode payload of the wrong
  architecture passes validation and fails at run time, not at build time.
- Capability mismatch: **hard error** (`validate_capabilities`); the hollowing
  target is a hard error too when the file resolves locally, and unchecked
  otherwise (`$arg.N$`, a remote path, a missing file).
- x86 indirect syscalls: **parked** (see M4). Revisit only with a Heaven's Gate
  design, which is its own project.
- Default hollowing target for `arch: x86`: **left as `System32\svchost.exe`**,
  which WOW64 resolves to the 32-bit image; documented, and the new target check
  maps the path the same way.
- .NET payloads: **`format: dotnet` (explicit) + `technique: dotnet_hosting`**,
  not silent auto-detection. A managed image packed as `pe`/`dll` is rejected at
  build time with a message that names the right combination, which is the part
  of auto-detection that was worth having; the format itself stays explicit so a
  plan always says what it delivers. `format: dotnet` and `dotnet_hosting` imply
  each other, and a managed payload whose bitness does not match `output.arch`
  (e.g. a `32BITREQUIRED` assembly with `arch: x64`) is a build error.
- .NET hosting runs the assembly in the **stub's** process (the CLR is hosted
  there), so it is only compatible with `reflective_loading`: `dotnet_hosting` is
  an execution technique and a pipeline has exactly one, so a plan that also
  names `process_hollowing` is rejected by the pipeline rule (and a hollowed
  target has no hosting stub of its own).
